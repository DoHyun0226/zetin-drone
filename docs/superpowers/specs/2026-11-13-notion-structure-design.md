# 노션 드론 페이지 재정리 설계 (2026-11-13)

대상: ZETIN 워크스페이스의 `드론` 페이지(`3142d27b08d3804eb85ced1ca13d8998`)와 그 하위 전부.
결과물: (1) 새 규칙으로 고친 `docs/notion_doc_convention.md`, (2) 그 규칙대로 정렬한 노션.

## 1. 왜

팀원이 노션을 열었을 때 원하는 자료가 어디 있는지 따라가기 어렵다. 지금 상태:

- 제목 형식이 제각각이다(괄호 속 영어, ` · ` 나열, 날짜 위치, `2026-2_drone_ver.1` 같은 밑줄 제목).
- 아이콘은 하위 19쪽 가운데 일부에만 있고 제각각이다.
- 페이지마다 상태 콜아웃이 있고(🚦/📌/🚁/없음) 길다. "원본 위치는 확인이 필요하다",
  "명령·상수·필드 규격은 레포가 정본이다…" 같은 메타 설명이 내용보다 먼저 나온다.
- 같은 페이지가 여러 곳에 링크돼 있다(지상국 3곳, 08-18~19 기록 4곳, 백로그 3곳).
- 틀리거나 낡은 문장이 있다(파일이 첨부돼 있는데 "확인 필요", "최근 시험" 링크가 08-18~19,
  10-30 기록이 없는 `flow_hold` 경로를 가리킴, 비행 기록·백로그 콜아웃의 깨진 글자
  "처회된 관상/노션 줍에서도/자동착륙로").

사용자가 원하는 그림: **HW 팀원이 "PCB C4가 뭐였지" 하면 HW › PCB v1.5.2 › BOM 으로 들어가서
바로 본다.** 장황한 설명이 아니라 깔끔하게 정리정돈된 느낌. 계층이 깊어지는 것은 괜찮다.

## 2. 목표 · 비목표 · 반목표

- 목표: 팀 파트별로 길을 찾는 구조, 짧고 일관된 제목, 종류별 아이콘, 페이지를 열면 바로 내용.
  로컬 `docs/materials/` 자료를 맞는 노션 페이지에 올려 노션 안에서 받을 수 있게 한다.
- 비목표: 설명형 페이지의 기술 내용을 새로 쓰거나 검증하는 일. 이번 일은 정리다.
  내용 수정은 메타 문장 제거, 틀린 문장·깨진 글자·끊긴 링크·중복 링크 정리에 한정한다.
- 반목표(이렇게 되면 실패):
  - 정리하다 내용(측정값, 시험 조건, 정정 기록, 체크 상태, 첨부 파일)이 사라진다.
  - 페이지는 늘었는데 비어 있다(내용 없는 허브 페이지).
  - 기록형 페이지의 본문이 바뀌어 과거 기록이 바뀐다.
  - 레포가 정답인 수치를 노션에 새로 옮겨 적는다.
  - 파일이 어느 보드·기체 버전 것인지 모르는 채로 "현행 자료" 자리에 놓인다.

## 3. 사용자가 정한 것

| 항목 | 결정 |

| 맨 위 분류 | 팀 파트별: 🔧 HW · 💻 SW · 📐 CAD, 그리고 파트를 가리지 않는 자료용 🛩️ 공통 |
| 제목 | 부모가 맥락을 맡고 제목은 짧게(예: `PCB v1.5.2` 아래 `BOM`, `회로도`). 기록형만 날짜를 앞에(`2026-10-30 광류 위치 유지 테더 비행`) |

| 회의 | 2026-10-10 빈 회의 노트와 2026-09-21 회의록은 새 구조에 올리지 않는다 → 회의 토글 없음 |

## 4. 지키는 기존 제약

- 드론 페이지 최상위 골격은 `동아리 프로젝트` DB 템플릿이다: `활동 한 줄 소개` 토글 → 현재 상태
  → `## 📋 결과` → `## ⚠️ 안전 수칙` → `## 🗓 활동 로그 · 마일스톤`. 바꾸지 않는다.
- 수치의 정답은 레포다(옛 컨벤션 §0). 기록형은 본문을 고치지 않고 정정을 병기한다(옛 §2).
- 노션은 ZETIN 워크스페이스(`a622d27b-08d3-81e5-bf6c-0003781fc028`)만. 작업 전 `get-self` 로 확인.
- 레포는 공개다. 이 문서와 컨벤션 문서에 팀원 이름·학번 등을 쓰지 않는다.

## 5. 새 구조

`## 📋 결과` 아래에 파트 **토글** 네 개를 둔다. 그 안의 대상(보드·기체·기능)은 **페이지**이고,
대상의 하위 자료(BOM·회로도 등)는 그 페이지의 **하위 페이지**다.

```
## 📋 결과
▸ 🔧 HW
   📎 PCB v1.5.2          거버·회로도·배치 파일 (BOM 원본은 아직 없음)
   📎 Drone-Dev-Kit V4     2026-01 BOM csv — v1.5.2 와 다른 보드로 보임
   📄 기체 구성            ← 「하드웨어 구성 · BOM」
▸ 💻 SW
   [레포] 링크 한 줄
   ▸ 펌웨어
      📄 하드웨어 통신
      📄 필터
      📄 BMM350 yaw 융합   ← 「BMM350 Yaw 융합 · 모터 전류 간섭 보정」
      📄 3901-L0X 광류·거리계
      📄 PID 제어
      📄 자동착륙          ← 「자동착륙 (Failsafe Auto-Land)」
      📄 카메라 보드        ← 「카메라 보드 (ESP32-CAM) 영상 스트림」
   ▸ 지상국
      📄 UDP 통신
      📄 텔레메트리         ← 「텔레메트리 · 1kHz 원시 스트림 (ZIMU/ZCAL)」
      📄 지상국            ← 「지상국 · 작업 흐름 · 검증」 (처음 참여·작업 순서 절은 시작하기로)
▸ 📐 CAD
   📎 2026-2 기체          ← 「2026-2_drone_ver.1」
      📎 ver.1 (2026-09)   ← 하위 「CAD file」
      📎 최종 형상 (2026-11) 새 하위 페이지 — 로컬 STEP·렌더
   📎 2026-1 기체          ← 「Drone Legacy Modeling(~2026-1)」
▸ 🛩️ 공통
   📄 시작하기             새 페이지 — 지상국 페이지의 처음 참여·작업 순서 절을 옮김
   ☑️ 할 일                새 페이지 — 지금 유효한 할 일
   ▸ 비행 기록   (최신이 위)
      📅 2026-11-02~03 카메라 스트림·지상국 벤치
      📅 2026-10-30 광류 위치 유지 테더 비행      ← 「… (flow-hold)」
      📅 2026-08-18~19 테더 이륙·호버·착륙 반복 시험
      📅 2026-08-01 첫 실비행·하강 시험          ← 「비행 기록 · 백로그 (2026-08-01 기준)」
   📎 발표·보고서·영상       새 페이지

(구조에서 빠지는 것) 「하드웨어 구성 · BOM」 아래 빈 회의 노트(2026-10-10) → 노션 휴지통(복구 가능)
```

`←` 는 옛 제목이다. 표에 없는 하위 페이지가 작업 중에 나오면 같은 규칙으로 자리를 정하고
결과 보고에 적는다.

### 내 판단으로 정한 것

- **파트는 토글, 대상은 페이지.** 파트를 페이지로 만들면 클릭이 하나 늘고 그 페이지는 목록뿐이다
  (빈 허브). 대상(PCB v1.5.2, 2026-2 기체)은 파일과 하위 자료를 담으니 페이지다. 경로는
  `드론 › PCB v1.5.2 › BOM`.
- **카메라 보드는 펌웨어 아래.** 별도 보드(ESP32-CAM)지만 그 보드의 펌웨어 설명이다.
- **2026-2 기체를 ver.1 과 최종 형상으로 나눈다.** 노션 「CAD file」(2026-09-30)에는
  `drone_v1_frame.f3d/.step`, `drone_v1_housing_streamline/phantom.step`, `stl_print_parts.zip` 이 있고,
  로컬 `cad/2026-2-shell/` 은 2026-11-12 최신 형상(`FINAL.step`, `b_drone.step`, 렌더)이다. 같은 이름의
  `drone_v1_frame.step` 은 해시로 대조해 같으면 다시 올리지 않는다.
- **처음 참여·작업 순서는 `📄 시작하기` 로 뗀다.** 옛 컨벤션 §8 이 요구한 "처음 읽을 곳"을 지상국
  제목 뒤에 숨기지 않고 공통 맨 위에 둔다.

## 6. 규칙 (컨벤션 문서에 들어갈 내용)

### 제목

- 짧은 명사구. 부모 페이지·토글이 말해 주는 것은 제목에서 반복하지 않는다.
- 괄호 속 영어 풀이, ` · ` 로 여러 주제 나열, 밑줄·하이픈 슬러그를 쓰지 않는다.
  괄호는 버전·날짜 구분(`ver.1 (2026-09)`)에만.
- 부품·보드·프로토콜 이름은 원래 표기(`BMM350`, `3901-L0X`, `PCB v1.5.2`, `UDP`). 일반 단어는 한국어,
  영어 일반어는 소문자(`yaw`).
- 버전은 `v` + 숫자(`v1.5.2`), 학기는 `2026-2`.
- 기록형: `YYYY-MM-DD 내용`. 여러 날이면 `YYYY-MM-DD~DD`.

### 아이콘

- 파트 토글: 🔧 HW, 💻 SW, 📐 CAD, 🛩️ 공통. 하위 분류 토글(펌웨어·지상국·비행 기록)은 아이콘 없음.
- 페이지는 종류로 하나: 📄 설명형, 📅 기록형, 📎 자료(파일이 주인 페이지), ☑️ 할 일.
- 드론 페이지 자체 아이콘은 DB 템플릿을 따른다(지금 없음, 그대로 둔다).

### 페이지 본문

- 첫 블록부터 내용이다. 머리의 상태 콜아웃, "이 페이지는 …", "레포가 정본이다" 같은 메타 문장을 두지 않는다.
- **설명형은 맨 아래 한 줄에 `레포:` 관련 파일 링크와 `확인:` 날짜·근거(코드 대조 / 벤치 / 테더 비행 /
  실비행)를 둔다.** 근거가 여럿이면 짧게 나열한다(예: `확인: 코드 대조 2026-09-07 · 실물 기록 2026-08-24`).
  옛 상태 콜아웃의 검증 정보는 지우지 않고 이 줄로 옮긴다. 콜아웃 안에 측정값·주의 문구가 있었으면 본문의
  해당 절로 옮긴다.
- 자료 페이지(📎)는 파일 블록과, 파일마다 무엇인지·어느 버전 것인지 한 줄. 버전 대응을 모르면 "대응 미확인"
  이라고 쓴다. 같은 파일(해시 기준)을 두 번 올리지 않는다.
- **분류 토글**(파트·하위 분류) 안에는 페이지·파일·링크·하위 분류 토글만 둔다. 분류를 설명하는 문장
  ("센서 → 추정 → … 순서로 읽는다")은 쓰지 않는다. 본문 안에서 내용을 접는 토글(예: 기체 구성의
  "2026-08-24 예비 비용·제작시간 기록")은 이 규칙 대상이 아니다.
- 한 페이지는 한 곳에만 둔다. 다른 곳에서 가리킬 때는 mention 링크.

### 드론 페이지 맨 위

- `활동 한 줄 소개` 토글: 그대로.
- 현재 상태 콜아웃: 마지막 비행 / 검증된 것 / 아직 안 된 것 / 다음 목표 네 줄을 **각 한 줄**로
  줄인다. 자세한 내용은 해당 페이지 링크로.
- 결과 토글 위의 링크 줄·📌 콜아웃은 없앤다(레포 링크는 SW 토글 첫 줄, 처음 참여는 `📄 시작하기`).
- 안전 수칙·활동 로그: 그대로.

### 기록형

- 제목·아이콘·위치는 바꿔도 된다(정리). **본문은 고치지 않는다 — 머리 콜아웃·백로그 절 포함.**
- 예외: 깨진 글자(의미 없는 오타)와 끊긴 링크는 고친다. 사실이 틀린 문장은 정정 병기.
- 기록 안의 백로그는 그 자리에 둔다. `☑️ 할 일` 은 지금 유효한 항목만 새로 모은 목록이고, 기록에서 가져온
  항목에는 출처 기록을 mention 으로 단다.

### 할 일

- 출처: 2026-11-12 향후 계획(`docs/materials/plans/2026-11-12_future_plan.md`), 지상국 페이지의 현재 할 일,
  기록형의 백로그 가운데 아직 열린 항목. 완료·폐기된 것은 옮기지 않는다(원래 기록에 그대로 있다).
- 파트(HW·SW·CAD·공통)로 묶는다. 담당자·일정은 확인된 것만 쓴다.
- 완료해도 지우지 않고 체크 + 결과 한 줄(옛 §2 백로그 규칙 유지).

### 갱신 시점·안전 서술

- 옛 §5 를 유지하되 "상태 콜아웃(검증 수준·날짜)을 같이 갱신"은 "설명형 맨 아래 `확인:` 줄과 드론 페이지
  현재 상태를 같이 갱신"으로 바꾼다.
- 새 파일·새 버전이 생기면 해당 📎 페이지에 파일과 버전 한 줄을 더한다. 옛 파일은 지우지 않는다.
- 옛 §6(안전 서술) 그대로.

## 9. 작업 순서와 확인

1. `get-self` 로 ZETIN 확인. 드론 페이지와 하위 전부를 fetch 해 스크래치패드에 저장하고, **페이지 ID →
   옛 부모·옛 제목·새 부모·새 분류 토글 경로(예: `결과 › 💻 SW › 펌웨어`)·새 제목·아이콘** 대조표를 만든다. 기존 첨부는 `get_file_download_urls` 로 받아
   해시를 남긴다.
2. 컨벤션 문서 개정(레포). CLAUDE.md·AGENTS.md 포인터 블록 문구도 같이 맞춘다.
3. 노션: 새 페이지 생성 → 파일 업로드 → 옮기기(`move-pages` 로 실제 부모에 먼저 옮긴 뒤 토글 안 배치 —
   옛 컨벤션 §1 함정 절차를 부모가 드론이 아닐 때로 일반화) → 제목·아이콘 → 설명형 본문 정리
   (머리 콜아웃 → `레포:`·`확인:` 줄, 깨진 글자, 끊긴 링크, 중복 링크) → 할 일·시작하기 → 드론 페이지.
4. 확인(합격 조건):
   - (a) 대조표의 모든 페이지가 기대한 부모의 실제 자식이고(mention 이 아니라 `<page>`), 그 `<page>` 가
     기대한 분류 토글 경로 안에 있다.
   - (b) 제목·아이콘이 규칙대로다. 설명형에 머리 상태 콜아웃이 남지 않았다.
   - (c) 페이지마다 1단계 저장본과 본문 전체를 diff 해서, 바뀐 곳이 모두 허용한 변경(메타 문장 제거,
     콜아웃 → `확인:` 줄 이동, 오타·링크 수정, 옮긴 절)이고 각각 이유·옮긴 위치를 작업 기록에 남겼다.
     기록형은 제목·아이콘·깨진 글자·링크 외 diff 가 없다.
   - (d) 기존 파일 블록이 모두 남아 있고 받을 수 있다. 새 자료는 7절 표의 줄마다 올림 / 기존 것과 같아 생략 /
     제외 / 실패 중 하나로 처리 결과가 있다.
   - (e) 링크가 살아 있다.
5. 되돌리기: 페이지 위치는 `move-pages` 로, 본문은 노션 페이지 버전 기록(`restore-version`)으로 되돌린다.
   스크래치패드 저장본은 diff 와 대조용이다.
6. 레포 변경(컨벤션·지침·이 설계)은 사용자 확인 후 커밋.
