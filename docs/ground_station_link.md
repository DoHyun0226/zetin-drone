# 지상국 링크 요구사항과 RC 타임아웃 진단

이 문서는 현행 지상국의 링크 상실 대응과 로그 진단법을 설명한다.
2026-07-27 사례는 뒤에 당시 기록으로 보존한다. 그 사례의 빌드·장비·측정값을
현재 기체의 상태로 적용하지 않는다. 현행 설명은 2026-09-07 저장소 코드와
대조했으며, 실제 연결 장비의 동작은 별도 확인해야 한다.

## 1. 링크 상실·수동 정지·복구를 구분한다

펌웨어는 마지막 유효 `rc`/`rcr` 수신 이후 500ms를 초과하면 `Fault_RC`를
세운다. `connect`·`th`·PID 명령은 RC 워치독을 갱신하지 않는다.
호버 추정 미확정 또는 낮은 기본 스로틀에서는 즉시 컷하고, 그 외에는
`Failsafe_Phase=1`로 들어가 호버 추정치를 기준으로 시간 기반 하강을 한다.
즉시컷 조건은 소프트웨어 정책이며 기체가 물리적으로 지상에 있다는 증명이 아니다.

**현행 하강은 착지를 감지하지 않는다.** 진입 후 3초 백스톱에서 phase 3으로
컷하고, `stop`·IMU 전멸·과도 기울기 등 안전 중단은 phase 4로 컷한다.
프로브는 진단을 위해 작동하지만 그 결과로 phase 2 착지컷을 만들지 않는다.
접지 후에도 남은 시간만큼 모터가 돌 수 있고, 초기 고도·추정 오차에 따라
백스톱 때 공중일 가능성도 이 시간만으로 배제할 수 없다. 정확한 분기·상수는
[UDP 프로토콜](udp_protocol.md#지상국--드론)이 정본이다.

| 상황 | `control_dualsense.py`의 동작 | 드론 상태 확인 |
|---|---|---|
| 게임패드 분리·텔레메트리 1.5초 미수신·`Fault_RC` 상승 엣지 | RC 송신만 중단. `stop`·`th 1000` 미전송 | 수신이 있으면 `Armed`와 `Failsafe_Phase`를 함께 확인 |
| X·stdin `stop`·Ctrl+C | 수동 `stop` 경로. X와 Ctrl+C는 로컬 무장 추정에 따름 | 전송 자체는 컷 완료 ACK가 아님 |
| 연결 복구 | RC 자동 재개 없음 | 하강 중 조건을 충족하면 △·stdin `resume` 요청 |
| `resume` 요청 | RC 수락 확인 → `resume` 전송 → 추가 RC 수락과 phase 0 확인 | 성공 메시지 전까지 복귀를 확정하지 않음 |

수신이 끊기면 지상국은 현재 기체의 무장·하강 상태를 확정할 수 없다.
`is_streaming`은 로컬 RC 송신 여부이고, `is_armed`는 무장 상태에 대한
지상국의 추정이다. RC를 멈춘 뒤에도 이 추정을 유지해 수동 정지를 계속
요청할 수 있게 한다. X는 토글이므로 무장 추정이 이미 지워진 뒤에는 시동을
요청한다. **정지만 요청하려면 stdin `stop`**을 사용한다.

`resume`은 같은 실행 세션에서 최신 하강·호버 텔레메트리가 있을 때만
시작한다. 펌웨어가 컷한 뒤에는 복귀할 수 없고, 성공해도 잃은 고도와 하강속도를
자동 복구하지 않는다. 지상국 상세 조건과 실패 후 상태는
[도구 안내](../scripts/README.md#링크가-끊겼을-때)를 참고한다.
RC 타임아웃을 늘리기 전에 송신·링크·펌웨어 수신 경로를 먼저 진단한다.

## 2. 연결 준비

비행용 DualSense는 **USB로 연결한다.** WiFi/BT 라디오를 공유한 과거 장비에서
블루투스 사용과 RC 정체가 함께 관측됐다. 무선 패드를 평가하려면 별도 WiFi
라디오를 포함한 구성으로 링크를 다시 측정해야 한다. AP 채널 변경만으로
공유 라디오의 경합이 제거된다고 가정하지 않는다.

- 드론에 UDP를 보내는 프로그램은 하나만 실행한다. `connect`만 보내는
  수신기도 목적지를 가져갈 수 있다.
- 비행 중 노트북 서스펜드·자동 네트워크 전환을 막는다.
- WiFi 인터페이스 이름은 `iw dev`로 확인한다. 아래 `wlan0`은 예시다.
- 무장 전 `iw dev wlan0 link`에서 실제 `Drone_Tuning` 연결을 확인한다.
- `nmcli -f 802-11-wireless.powersave connection show Drone_Tuning`으로
  프로파일의 절전 상태를 확인한다. 이 프로젝트의 비행 링크는 절전 비활성
  설정을 사용한다.

## 3. 텔레메트리가 살아 있어도 조종은 끊길 수 있다

다운링크 수신과 업링크 송신의 지연·유실은 같지 않다. 공유 WiFi/BT 라디오,
OS 스케줄링, 지상국 스레드의 블로킹, 드라이버 큐, 무선 재전송, 펌웨어 파서
모두 조사 대상이다. 텔레메트리가 계속 오는 사실만으로 PC 측 단일 원인을
확정할 수 없다.

2026-07-27에는 USB/BT 전환과 RC 정체의 강한 상관관계가 기록됐다.
BT airtime 경합이 관측 방향과 맞지만, 수백 ms 정체까지 증폭된 내부 경로는
슬롯·큐 단위로 측정되지 않았다. 아래 사례의 “원인 배제” 표현은 당시
판정으로 읽고, 새 장애에는 같은 결론을 자동 적용하지 않는다.

## 4. 로그로 좁히는 법

| 관찰 | 가능한 해석과 다음 확인 |
|---|---|
| RC 카운터 정체 중 텔레메트리 수신 지속 | 같은 `udp_task`가 송신을 계속한 근거. 지상국 송신 지연·업링크·RC 파싱/순서 거부를 확인 |
| RC와 텔레메트리 모두 정체 | 양방향 링크 또는 태스크 지연 가능. PC 수신 프로세스 정체도 확인 |
| `RC_Dropped_Pkts` 불변 | 관측 구간에서 시퀀스 틈/폐기 증가를 못 봄. 아직 도착하지 않은 유실은 카운터에 드러나지 않을 수 있음 |
| 복구 시 `RC_Total_Pkts` 급증 | 버스트 도착 가능. PC 송신 로그·수신 간격을 함께 대조 |
| `PID_Loop_Hz`가 약 1000 | 보고된 평균 루프율이 유지됨. 개별 tick 지연·실제 모터 반응까지 증명하지 않음 |

`RC_Total_Pkts`는 형식이 유효한 시퀀스 RC 데이터그램의 처리 횟수이며
나중에 중복/오래된 것으로 거부되는 것도 포함한다. `RC_Dropped_Pkts`는
**수신 시퀀스 틈 + 중복/오래된 패킷 폐기**를 합친 값이다. 따라서 단순한
무선 유실 개수도 아니고, `Total − Dropped`가 정확한 수락 개수인 것도 아니다.
무시퀀스 벤치 `rc`는 이 두 카운터를 올리지 않는다. 세부 계약은
[UDP 프로토콜](udp_protocol.md#rc-순서와-카운터)을 참고한다.

### 구간별 RC 레이트

현행 `control_dualsense.py` 송신 목표는 **20Hz**(`CTRL_LOOP_HZ=20`)다.
정상 구간에서는 수신 증가율이 이에 가까워야 하지만 평균 20Hz만으로 500ms
공백이 없었다고 판단할 수 없다. 카운터는 `start` 때 리셋되지 않으므로
무장 구간의 마지막 값에서 첫 값을 뺀 증분을 시간으로 나눈다. 재부팅·uint32
래핑·PC 자정/시계 변경이 있는 구간은 먼저 분리한다.

```text
구간 RC 처리율 = ΔRC_Total_Pkts / ΔPC 수신시각
구간 폐기/틈 증가 = ΔRC_Dropped_Pkts
```

중복 패킷도 Total에 포함되므로 이 값은 “유효한 조종 명령 수락률”과 구분한다.
평균 외에 연속 텔레메트리에서 RC 카운터가 멈춘 길이, `Fault_RC` 상승 시점,
복구 버스트를 함께 확인한다.

### 링크 측정

```bash
ping -D -i 0.02 -c 500 192.168.4.1
iw dev wlan0 station dump
```

프로펠러를 제거한 링크 진단에서 USB/BT 조건을 나눠 RTT와 손실·`tx retries`·
`tx failed` 변화를 비교한다. ping은 ICMP 경로 측정이므로 RC 전달의 직접
검증은 아니다. 송신 재시도 증가만으로 BT 점유 경합을 단정할 수도 없다.

## 5. 사례: 2026-07-27 RC 타임아웃 연발

### 증상

03:51 이후 모든 비행이 무장 후 1.8~9.9초 만에 `Fault_RC`로 정지.

### 근본 원인

**02:48:16에 DualSense를 USB에서 뽑고, 03:50:42에 블루투스로 재연결한 것.**

```text
03:50:42  playstation 0005:054C:0CE6.0006:
          BLUETOOTH HID v1.00 Gamepad [DualSense Wireless Controller]
03:51:06  ← 첫 번째 불량 로그
```

### 상관관계 (예외 0건)

| 시간대 | 패드 연결 | 무장 구간 rc 레이트 | 결과 |
|---|---|---|---|
| 01:20~02:25 | **USB** (Bus=0003) | 20.0~20.1Hz | 정상 (15~43초 유지) |
| 02:37~02:48 | **USB** | 20.0~20.1Hz | 정상 |
| **03:50:42~** | **블루투스** (Bus=0005) | **13.3~19.6Hz** | **전 구간 RC 타임아웃** |

USB 8개 구간 전부 정상, 블루투스 6개 구간 전부 실패.

### 배제된 원인

- **펌웨어**: 정상 세션(02:38, 02:43)과 불량 세션이 **같은 빌드**(둘 다 34필드
  텔레메트리, commit `1497d74`). 그 사이 코드 변경 없음.
- **BMM350 mag 융합**: 01:45부터 켜져 있었고 그 세션들은 20.0Hz 무결점.
  `mag 1`은 무죄다.
- **공중 패킷 유실**: 정지 구간 내내 `RC_Dropped_Pkts`가 34에서 불변.
- **드론 측 정지**: rc가 450ms간 0건인 동안 텔레메트리는 47/50/50/51/49/50/53ms로
  완벽히 규칙적. 복구 시 `RC_Total`이 313 → 314 → 320으로 버스트 도착.

### 부수 요인

같은 시간대에 노트북이 1시간에 4번 서스펜드했다(02:31, 03:44, 03:44:17, 03:50).
03:50 복귀 직후 NetworkManager가 `Member@UOS`로 자동 접속했고, `Drone_Tuning`으로
되돌릴 때 첫 association이 실패했다(`disconnected during association`, BSSID
10초 차단). 비행 세션 중 절전은 꺼둘 것.
