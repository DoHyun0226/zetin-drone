# 노션 문서 컨벤션 (2026-11-13 개정)

대상: 노션 `로봇연구회 ZETIN > … > 드론` 페이지 전체와 그 하위 전부.
https://app.notion.com/p/3142d27b08d3804eb85ced1ca13d8998

목표는 팀원이 노션을 열었을 때 원하는 자료로 바로 따라갈 수 있는 것이다. 설명을 늘어놓기보다
정리정돈을 우선한다. 설계 배경은 [재정리 설계](superpowers/specs/2026-11-13-notion-structure-design.md).

## 0. 정답은 레포다 (SSOT)

- 상수, 텔레메트리 필드 번호, UDP 명령 문법, 바이너리 규격의 **정답은 `docs/`와
  `firmware/`**다. 노션은 그 값을 옮겨 적는 곳이 아니다.
- 노션에는 **왜 그렇게 됐는지, 무엇을 측정했는지, 무엇을 배웠는지**를 쓴다.
- 수치를 꼭 인용해야 하면 출처 파일 경로를 같이 적는다.
- 노션과 레포가 어긋나면 **레포가 맞다.** 노션을 고친다.

## 1. 구조 — 파트 토글 아래 대상 페이지

`## 📋 결과` 아래에 **파트 토글** 네 개를 둔다. 토글 안의 대상(보드·기체·기능)은 **페이지**,
대상의 하위 자료(BOM·회로도·버전별 파일)는 그 페이지의 **하위 페이지**다.

```text
## 📋 결과
▸ 🔧 HW     보드·전장 (PCB v1.5.2, 기체 구성 …)
▸ 💻 SW     첫 줄에 레포 링크 / ▸ 펌웨어 / ▸ 지상국
▸ 📐 CAD    기체 버전별 (2026-2 기체 › ver.1 (2026-09), 최종 형상 (2026-11) …)
▸ 🛩️ 공통   📄 시작하기 · ☑️ 할 일 · ▸ 비행 기록 · 📎 발표·보고서·영상
```

- 파트 토글과 하위 분류 토글(펌웨어·지상국·비행 기록)은 페이지가 아니다. 목록만 있는 허브
  페이지는 만들지 않는다.
- 한 페이지는 한 곳에만 둔다. 다른 곳에서 가리킬 때는 mention 링크.
- 하위 분류 토글 안의 순서: 펌웨어는 신호 흐름 순(하드웨어 통신 → 필터 → BMM350 → 3901-L0X →
  PID 제어 → 자동착륙 → 카메라 보드), 지상국은 UDP 통신 → 텔레메트리 → 지상국, 비행 기록은
  최신이 위.

### MCP로 토글 안에 페이지를 넣을 때 (함정)

`create-pages`는 토글 블록을 부모로 받지 못한다.

1. 페이지를 **실제 부모 페이지**의 자식으로 만든다(`create-pages`) 또는 옮긴다(`move-pages`).
   새 페이지는 부모 페이지 맨 끝에 붙는다.
2. 부모 페이지를 `update-page`(`update_content`)로 고쳐 목표 토글 안에 `<page url="...">제목</page>`
   줄을 넣고 맨 끝의 같은 줄을 지운다. 한 번의 호출에서 둘 다 한다.

**대상이 그 부모의 실제 자식이 아니면** `<page>`가 조용히 `<mention-page>`(단순 링크)로 바뀌고
이동은 일어나지 않는다. 1단계를 먼저 한다.

## 2. 페이지 유형

| 유형 | 아이콘 | 내용 | 고치는 방식 |
|---|---|---|---|
| 설명형 | 📄 | 현재 동작 | 늘 최신으로. 바뀌면 과거 서술을 남기지 말고 고친다 |
| 기록형 | 📅 | 날짜가 박힌 측정·시험 | **본문 불변**(머리 콜아웃·백로그 절 포함). 틀린 것은 정정 병기 |
| 자료 | 📎 | 파일이 주인(보드·기체·발표) | 새 파일·버전은 더하고 옛 파일은 지우지 않는다 |
| 할 일 | ☑️ | 지금 유효한 작업 | 완료해도 지우지 않고 체크 + 결과 한 줄 |

- 기록형에서 바꿔도 되는 것: 제목·아이콘·위치, 깨진 글자(의미 없는 오타), 끊긴 링크.
- 기록 안의 백로그는 그 자리에 둔다. `☑️ 할 일`은 지금 열린 항목만 새로 모은 목록이고,
  기록에서 가져온 항목에는 출처 기록을 mention 으로 단다. 담당자·일정은 확인된 것만 쓴다.

## 3. 제목

- 짧은 명사구. 부모 페이지·토글이 말해 주는 것은 반복하지 않는다(`PCB v1.5.2` 아래 `BOM`).
- 괄호 속 영어 풀이, ` · `로 여러 주제 나열, 밑줄·하이픈 슬러그를 쓰지 않는다. 괄호는 버전·날짜
  구분(`ver.1 (2026-09)`)에만.
- 부품·보드·프로토콜 이름은 원래 표기(`BMM350`, `3901-L0X`, `PCB v1.5.2`, `UDP`). 일반 단어는
  한국어, 영어 일반어는 소문자(`yaw`).
- 버전은 `v` + 숫자(`v1.5.2`), 학기는 `2026-2`.
- 기록형: `YYYY-MM-DD 내용`, 여러 날이면 `YYYY-MM-DD~DD`.

## 4. 아이콘

- 파트 토글: 🔧 HW, 💻 SW, 📐 CAD, 🛩️ 공통. 하위 분류 토글은 아이콘 없음.
- 페이지: 유형마다 하나(2절 표). 다른 아이콘을 쓰지 않는다.
- 드론 페이지 자체 아이콘은 DB 템플릿을 따른다.

## 5. 페이지 본문

- **첫 블록부터 내용이다.** 머리 상태 콜아웃, "이 페이지는 …", "레포가 정본이다" 같은 메타
  문장을 두지 않는다. 이미 있는 기록형 페이지의 머리 콜아웃은 본문 불변 규칙(2절)에 따라 그대로
  둔다. 새로 만드는 기록형에는 두지 않는다.
- **설명형은 맨 아래 한 줄**에 관련 레포 파일과 확인 근거를 둔다.
  예: `레포: fc/pid_task.h · 확인: 코드 대조 2026-11-13 · 테더 비행 2026-10-30`.
  확인 근거는 코드 대조 / 벤치 / 테더 비행 / 실비행 중에서 날짜와 함께.
- 자료 페이지는 파일 블록마다 바로 아래에 무엇·어느 버전인지 한 줄. 모르면 `대응 미확인`.
  같은 파일(해시 기준)을 두 번 올리지 않는다.
- **분류 토글** 안에는 페이지·파일·링크·하위 분류 토글만 둔다. 분류를 설명하는 문장은 쓰지
  않는다. 본문 안에서 내용을 접는 토글은 이 규칙 대상이 아니다.

## 6. 표기

- 한국어로 쓴다. 코드 식별자·파일 경로·명령은 인라인 코드.
- 수식은 유니코드만: µs, °, ±, ≈, √, σ, ², ×, →. LaTeX 금지.
- 위키링크 `[[...]]` 금지. 실제 노션 링크나 레포 경로를 쓴다.
- 함수·상수 표는 3열 기본형: 대상 / 하는 일 / 핵심 포인트.
- 본문 콜아웃 아이콘: ⚠️·🚨 위험, ✅ 검증됨, 🕳️ 미측정·공백. 옛 기록형에 남은 🚦·📌 콜아웃은 그대로 둔다.

## 7. 갱신 시점

- **main에 머지될 때** — 해당 설명형 페이지와 그 맨 아래 `확인:` 줄을 고친다.
- **규격이 바뀔 때**(UDP 명령 추가, 텔레메트리 필드 append 등) — 그날 안에. 외부 계약이라 늦으면
  지상국 파서가 깨진다.
- **비행·벤치를 하면** — 기록형 페이지를 새로 만들고(비행 기록 토글 맨 위), 관련 설명형의 `확인:`
  줄과 드론 페이지 현재 상태를 같이 고친다.
- **새 파일·새 버전이 생기면** — 해당 📎 페이지에 파일과 버전 한 줄을 더한다.
- **세션이 끝날 때** — 그 세션에서 확정된 사실만 반영한다. 브랜치 상태는 적지 않는다(main에 머지된
  뒤에만 문서화).

## 8. 안전 관련 서술

- 실제 펌웨어 동작과 다른 안전 서술은 **버그로 취급**한다. 발견 즉시 정정한다.
- 20Hz 텔레메트리 값으로 안전 판정을 설명하지 않는다. IMU 불일치 `dG`는 20Hz에서
  실제보다 약 8배 작게 나온다. 판정 근거는 1kHz 원시 로그다.

## 9. 드론 페이지 맨 위

`동아리 프로젝트` DB의 기본 템플릿을 따른다. 이 골격은 다른 프로젝트 페이지와 공유하므로
임의로 바꾸지 않는다.

```text
▸ 활동 한 줄 소개              템플릿 필수 항목
🚁 현재 상태 (콜아웃)          마지막 비행 / 검증된 것 / 아직 안 된 것 / 다음 목표 — 각 한 줄
## 📋 결과                     파트 토글 네 개 (1절)
## ⚠️ 안전 수칙
## 🗓 활동 로그 · 마일스톤      날짜와 한 줄 요약, 최신이 위
```

- `현재 상태`와 `안전 수칙`은 `결과` 안에 넣지 않는다.
- `현재 상태`는 네 줄을 각 한 줄로 유지하고, 자세한 내용은 해당 페이지 mention 으로 연결한다.
- `결과` 위에 링크 줄이나 안내 콜아웃을 두지 않는다. 처음 참여 안내는 `🛩️ 공통 › 📄 시작하기`.
- DB의 요약·결과 속성에는 한 줄 소개와 검증 범위를 적는다. 확인하지 않은 팀명·담당자·진행
  상태를 만들지 않는다.

## 10. 이 문서가 규칙의 원본이다

**규칙을 바꿀 때는 이 파일을 고친다.** 에이전트별 프로젝트 지침(`.claude/CLAUDE.md`, `AGENTS.md`)은
이 문서를 가리키는 포인터 블록을 쓰고, 두 블록의 내용을 같게 유지한다(상대 경로만 다름).
